# ReturnDesk

A returns desk for a small online store. Support agents raise return requests, move them through a
fixed lifecycle, record a resolution (refund, replacement or store credit), leave notes, and take
requests off the desk without destroying them.

- **Live app:** https://returndesk-sepia-xi.vercel.app
- **Repository:** https://github.com/BITHAL04/RETURNDESK

## Features

All of the following are implemented and covered by automated tests.

- **Raise a request** with customer name, email, optional phone, order ID, item SKU, item name,
  quantity and reason. A unique human-readable reference (`RD-000123`) is generated by PostgreSQL.
- **Find requests**: search by customer name, email, order ID or reference; filter by one or more
  statuses and by reason; sort by reference, customer, status, created date; paginate. Everything
  runs in SQL on the server. Search is debounced (300 ms) in the UI.
- **Work a request**: full detail view with customer, order, item, decision and a chronological
  activity timeline that merges notes and audit history.
- **Lifecycle**: Open → In Review → Approved → Completed, or In Review → Rejected. Only the actions
  that are legal for the current status are offered.
- **Approval** requires a resolution; refunds require an amount greater than zero; other
  resolutions cannot carry an amount.
- **Edit** customer and item details while undecided; locked once Approved, Rejected or Completed.
- **Notes** can be added at any time (including after a decision) and can never be edited or deleted.
- **Remove** (soft delete) Open or Rejected requests; the record, notes and history are kept.
- **Dashboard** with live totals, status distribution, reason breakdown and recent requests.
- Loading skeletons, empty states, error states with retry, toasts, and server error messages shown
  to the agent. Usable down to 375 px with a dedicated mobile layout (drawer navigation, card list).

## Tech stack

| Layer      | Choice                                                                                                          |
| ---------- | --------------------------------------------------------------------------------------------------------------- |
| Framework  | Next.js 16 (App Router), React 19, TypeScript                                                                   |
| Backend    | Next.js Route Handlers (Node.js runtime), service + repository layers                                           |
| Database   | PostgreSQL 16 (Neon in production), **Drizzle ORM** + SQL migrations                                            |
| Validation | Zod 4 — one set of schemas shared by the API and the forms                                                      |
| UI         | Tailwind CSS 4, custom components, Radix Dialog, Motion (Framer Motion), Lucide, Sonner toasts, React Hook Form |
| Tests      | Vitest (unit + API integration against real Postgres), Playwright (E2E, desktop + 375 px)                       |
| Hosting    | Vercel + Neon                                                                                                   |

> **Why Drizzle and not Prisma?** I started with Prisma, but its CLI downloads a native schema
> engine from `binaries.prisma.sh` even to run `prisma generate`, and that host was blocked in my
> build environment. Drizzle is pure TypeScript, lets me express partial indexes and CHECK
> constraints in the schema, and keeps migrations as plain, reviewable SQL. The brief explicitly
> allows any query layer.

## Running locally

**Prerequisites:** Node.js ≥ 20.9 and a PostgreSQL 14+ server (local install or Docker).

```bash
# 1. Install
git clone https://github.com/BITHAL04/RETURNDESK.git returndesk && cd returndesk
npm install

# 2. Configure
cp .env.example .env
#    edit DATABASE_URL (and TEST_DATABASE_URL if you want to run integration tests)

# 3. Create the database (example for a local server; skip if it exists)
createdb returndesk

# 4. Build the schema from empty, then load sample data
npm run db:migrate
npm run db:seed

# 5. Run
npm run dev        # http://localhost:3000
```

Quick Postgres with Docker, if you don't have one:

```bash
docker run --name returndesk-pg -e POSTGRES_PASSWORD=postgres -p 5432:5432 -d postgres:16
docker exec returndesk-pg createdb -U postgres returndesk
docker exec returndesk-pg createdb -U postgres returndesk_test
```

## Architecture

A modular monolith with one-way dependencies:

```
src/app/(app)/…            pages (presentation)        ─┐
src/components/…           UI components                │ call the HTTP API via lib/api/client
src/app/api/…/route.ts     route handlers (HTTP layer) ─┼─► parse input with Zod, call service, wrap response
src/server/requests/service.ts    business rules        │   transactions, row locks, audit events
src/server/requests/repository.ts data access (SQL)     │   all filtering/sorting/paging in SQL
src/db/schema.ts + drizzle/*.sql  schema, constraints, triggers
src/lib/domain/            enums, labels, lifecycle rules (shared by server and UI)
src/lib/validation/        Zod schemas (shared by API and forms)
src/lib/errors.ts, lib/api/response.ts   error codes, response envelope, DB-error mapping
```

- **Route handlers are thin**: validate → call one service function → return the envelope. A shared
  `handler()` wrapper turns every thrown error into a consistent JSON error response.
- **The service layer owns the rules.** Every write runs in a transaction that row-locks the request
  (`SELECT … FOR UPDATE`), so two agents acting on the same request are serialised instead of racing.
- **The lifecycle is defined once** (`src/lib/domain/lifecycle.ts`). The API returns
  `actions: { transitions, canEditDetails, canRemove, canAddNote }` with every request, and the UI
  renders buttons from that — the frontend never re-implements the rules.
- **The database is the last line of defence**: constraints and triggers mirror every rule, so even a
  bug in application code cannot store an illegal state.
- The dashboard is a server component that reads the service directly; the list, detail and forms are
  client components that talk to the public HTTP API (the same API the tests exercise).

## Database design

Three tables, all with UUID primary keys and `timestamptz` timestamps.

**`return_requests`**

| Column                                              | Type                   | Notes                                                                                                                                                                                      |
| --------------------------------------------------- | ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `reference`                                         | `varchar(20)` UNIQUE   | Default `'RD-' \|\| lpad(nextval('return_request_reference_seq'), 6, '0')`. Generated by a sequence, so concurrent inserts can never collide; the API rejects a client-supplied reference. |
| `customer_name`, `customer_email`, `customer_phone` | `varchar`              | Phone nullable.                                                                                                                                                                            |
| `order_id`, `item_sku`, `item_name`                 | `varchar`              | SKU identifies the item on the order.                                                                                                                                                      |
| `quantity`                                          | `integer`              | CHECK `1..1000`.                                                                                                                                                                           |
| `reason`                                            | enum `return_reason`   | DAMAGED, WRONG_ITEM, SIZE_ISSUE, NOT_AS_DESCRIBED, CHANGED_MIND                                                                                                                            |
| `status`                                            | enum `request_status`  | Default OPEN.                                                                                                                                                                              |
| `resolution`                                        | enum `resolution` NULL | REFUND, REPLACEMENT, STORE_CREDIT                                                                                                                                                          |
| `refund_amount`                                     | `numeric(10,2)` NULL   | Money is never a float.                                                                                                                                                                    |
| `created_at`, `updated_at`, `deleted_at`            | `timestamptz`          | `deleted_at` = soft delete.                                                                                                                                                                |

**`notes`** — `request_id` FK (ON DELETE RESTRICT), `author`, `body` (CHECK non-blank, ≤ 5000), `created_at`.

**`request_events`** (audit history) — `request_id` FK, `type` (CREATED, DETAILS_UPDATED,
STATUS_CHANGED, REMOVED), `from_status`, `to_status`, `changes jsonb` (`{ field: { from, to } }`).

**Constraints, indexes and triggers**

| Object                                                                                                                                                                     | Enforces                                                                                                                                                                |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| CHECK `return_requests_resolution_matches_status`                                                                                                                          | A resolution exists **iff** status is APPROVED or COMPLETED (rule 2).                                                                                                   |
| CHECK `return_requests_refund_amount_matches_resolution`                                                                                                                   | REFUND ⇒ amount > 0; otherwise amount IS NULL (rule 2).                                                                                                                 |
| Partial UNIQUE index `return_requests_one_live_per_order_item` on `(lower(order_id), lower(item_sku)) WHERE status NOT IN ('REJECTED','COMPLETED') AND deleted_at IS NULL` | One live request per order item, case-insensitive, race-proof (rule 3).                                                                                                 |
| Trigger `return_requests_guard_update`                                                                                                                                     | Only legal status transitions (rule 1); customer/item fields frozen once decided (rule 4); resolution final once approved; removed rows read-only; reference immutable. |
| CHECK `return_requests_removable_status`                                                                                                                                   | Only OPEN/REJECTED rows can have `deleted_at` (rule 5).                                                                                                                 |
| Trigger `return_requests_forbid_delete`                                                                                                                                    | Physical `DELETE` is refused (rule 5).                                                                                                                                  |
| Triggers `notes_append_only`, `request_events_append_only`                                                                                                                 | Notes and history can never be updated or deleted.                                                                                                                      |
| B-tree indexes on `status`, `reason`, `created_at`; `(request_id, created_at)` on notes/events                                                                             | Filtering, sorting and timelines.                                                                                                                                       |
| `pg_trgm` GIN indexes on name, email, order ID, reference                                                                                                                  | Fast `ILIKE '%term%'` search.                                                                                                                                           |

Migrations live in `drizzle/`: `0000_extensions.sql` (pg_trgm), `0001_init.sql` (generated from
`src/db/schema.ts`), `0002_lifecycle_triggers.sql` (hand-written triggers). They build the schema
from an empty database; the integration test suite drops and re-creates the schema from these
migrations on every run.

## Business rules and where they are enforced

| Rule                         | Service (friendly error)                                                                                    | Database (backstop)                      | Tests                                                                                                                                                                    |
| ---------------------------- | ----------------------------------------------------------------------------------------------------------- | ---------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 1. Status flow               | `transitionRequest` → `canTransition` → **409 INVALID_STATUS_TRANSITION** (lists the allowed next statuses) | guard trigger                            | every illegal pair; concurrent approve vs reject → one 200, one 409                                                                                                      |
| 2. Approval needs resolution | `decisionFor` → **422 RESOLUTION_REQUIRED / INVALID_REFUND_AMOUNT**                                         | two CHECKs                               | no resolution; refund missing/0/negative; amount with replacement or store credit                                                                                        |
| 3. One live request per item | `findLiveDuplicate` → **409 DUPLICATE_LIVE_REQUEST** naming the existing reference                          | partial unique index (also covers races) | case-insensitive duplicate; still blocked in review/approved; allowed after rejected/completed/removed; 8 concurrent creates → exactly 1 succeeds; edit into a duplicate |
| 4. Locked once decided       | `updateRequest` → **409 REQUEST_LOCKED**                                                                    | guard trigger                            | customer, item and quantity edits refused for approved/rejected/completed; notes still allowed                                                                           |
| 5. Removal                   | `removeRequest` → **409 REQUEST_NOT_REMOVABLE**; removed rows → **404** everywhere                          | CHECK + no-delete trigger                | removable statuses; refused statuses; row, notes and history still in DB; GET/PATCH/transition/DELETE on removed → 404                                                   |

## API

All endpoints return JSON with one envelope:

```jsonc
// success
{ "success": true, "data": { ... }, "meta": { ... } }      // meta only on lists
// failure
{ "success": false, "error": { "code": "INVALID_STATUS_TRANSITION", "message": "A request cannot move from OPEN to COMPLETED. Allowed next statuses: IN_REVIEW.", "details": { "from": "OPEN", "to": "COMPLETED", "allowed": ["IN_REVIEW"] } } }
```

| Method & path                        | Purpose                                                                                                                                                                                                                                  | Success                                             |
| ------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- |
| `GET /api/requests`                  | List with `q`, `status` (repeatable or comma-separated), `reason`, `sort` (`createdAt` \| `updatedAt` \| `reference` \| `customerName` \| `status` \| `quantity`), `order` (`asc`\|`desc`), `page` (≥ 1), `pageSize` (1–100, default 20) | 200 + `meta: { page, pageSize, total, totalPages }` |
| `POST /api/requests`                 | Create. Body: `customerName, customerEmail, customerPhone?, orderId, itemSku, itemName, quantity, reason`. Unknown keys (e.g. `reference`, `status`) are rejected.                                                                       | 201 + `Location`                                    |
| `GET /api/requests/:id`              | Request + `notes` + `history` + `actions`                                                                                                                                                                                                | 200                                                 |
| `PATCH /api/requests/:id`            | Correct details (any subset of the create fields) while undecided                                                                                                                                                                        | 200                                                 |
| `DELETE /api/requests/:id`           | Soft delete (Open/Rejected only)                                                                                                                                                                                                         | 200 `{ id, reference, removedAt }`                  |
| `POST /api/requests/:id/transitions` | `{ to, resolution?, refundAmount? }`                                                                                                                                                                                                     | 200                                                 |
| `GET /api/requests/:id/notes`        | Notes, oldest first                                                                                                                                                                                                                      | 200                                                 |
| `POST /api/requests/:id/notes`       | `{ author, body }` — allowed in every status                                                                                                                                                                                             | 201                                                 |
| `GET /api/stats`                     | Dashboard totals                                                                                                                                                                                                                         | 200                                                 |

**Status codes**

| Code                                    | When                                                                                                                                                        |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 400 `VALIDATION_ERROR` / `INVALID_JSON` | Malformed body or query; `details` lists `{ field, message }` per problem.                                                                                  |
| 404 `REQUEST_NOT_FOUND`                 | Unknown, malformed or removed id. 404 `ROUTE_NOT_FOUND` for unknown API paths.                                                                              |
| 405 `METHOD_NOT_ALLOWED`                | e.g. `PATCH` or `DELETE` on a note — notes are append-only. Includes an `Allow` header.                                                                     |
| 409                                     | The request's current state or another request conflicts: `INVALID_STATUS_TRANSITION`, `REQUEST_LOCKED`, `REQUEST_NOT_REMOVABLE`, `DUPLICATE_LIVE_REQUEST`. |
| 422                                     | Well-formed approval data that breaks rule 2: `RESOLUTION_REQUIRED`, `INVALID_REFUND_AMOUNT`.                                                               |
| 500 `INTERNAL_ERROR`                    | Unexpected only. Logged server-side; no stack trace or SQL reaches the client.                                                                              |

Example:

```bash
curl -X POST localhost:3000/api/requests/<id>/transitions \
  -H 'content-type: application/json' \
  -d '{"to":"APPROVED","resolution":"REFUND","refundAmount":"49.90"}'
```

## Testing

```bash
npm test            # 126 unit + integration tests
npm run test:e2e    # 11 Playwright journeys (desktop 1440px + mobile 375px)
```

- **Unit** (`tests/unit`): the lifecycle table (every one of the 25 status pairs) and validation schemas.
- **API integration** (`tests/integration`): call the real route handlers against a real PostgreSQL
  database built from the migrations. They cover all five rules (including races), invalid payloads,
  search/filter/sort/pagination together, soft delete, notes immutability at the SQL level,
  405 handling and dashboard stats. Results are cross-checked with direct SQL to prove persistence.
- **End-to-end** (`tests/e2e`): raise → review → approve with refund → note after decision →
  complete → survives reload → found by search; duplicate refusal shown to the user; validation
  messages; edit → reject → remove → 404; filters and empty state; no horizontal overflow at 375 px
  and working mobile navigation.

## Deployment

Hosted on **Vercel** with **Neon** PostgreSQL.

- Vercel runs the `vercel-build` script: `npm run db:migrate && npm run db:seed && next build`.
  Migrations are idempotent (tracked in `drizzle.__drizzle_migrations`) and the seed skips rows that
  already exist, so every deploy is safe to repeat and never destroys data.
- Live at https://returndesk-sepia-xi.vercel.app. The production API was verified directly
  against all five business rules, validation errors, 404/405 handling and combined
  search/filter/sort/paging.
- `DATABASE_URL` (Neon pooled connection string) is set as a Vercel environment variable. No
  credentials are committed; `.env` is git-ignored and `.env.example` lists every variable.

## Design decisions and trade-offs

- **Rules in the service, mirrored in the database.** The service gives precise, user-friendly errors;
  constraints and triggers guarantee integrity even under concurrency or a future bug. The cost is
  that rules appear twice (TypeScript and SQL); I accepted that because the SQL side is deliberately
  small and declarative, and tests exercise both.
- **Row locks (`SELECT … FOR UPDATE`) instead of optimistic versioning.** Simple and correct for a
  support desk's write volume; the second of two simultaneous actions sees the new state and gets an
  honest 409.
- **Transitions are their own endpoint** (`POST /transitions`) rather than `PATCH { status }`, because
  a transition carries decision data, has its own validation and creates an audit event. `PATCH` is
  only for correcting details, which keeps rule 4 easy to reason about.
- **Rule 3 is keyed on order ID + item SKU, case-insensitively.** The order already identifies the
  customer, and keying on free-text customer fields would let a typo bypass the rule.
- **Removed requests return 404**, not 410, so the API does not reveal whether a removed record
  exists. Removed requests no longer block a new request for the same item.
- **409 vs 422.** 409 = conflicts with the resource's current state; 422 = the approval payload is
  well-formed but semantically invalid. 400 is reserved for malformed input.
- **Offset pagination** with a stable `id` tiebreaker. Fine for desk-sized data; keyset pagination
  would be the next step for very large tables.
- **References come from a sequence**, so gaps are possible (a failed insert consumes a number). That
  is normal and preferable to locking a counter row.
- **Drizzle over Prisma** — see [Tech stack](#tech-stack).
- **No authentication** (not in the brief). Notes record a free-text author name, remembered in the
  browser for convenience only.

## Assumptions

- An item on an order is identified by its SKU; the item name is descriptive only.
- A resolution is chosen at the moment of approval and is final afterwards.
- Rejected requests have no resolution.
- Quantity is between 1 and 1000; refunds are below 100,000,000 with at most 2 decimals; currency is
  shown as USD.
- A malformed request id is reported as 404 (it cannot identify any request).
- Soft-deleted requests are excluded from dashboard statistics.

## Known limitations and what I would do next

- No authentication/authorisation or per-agent assignment.
- No undo for removal (the data is retained, but there is no "restore" endpoint).
- Offset pagination; I would move to keyset pagination for large datasets.
- Search is substring matching (`ILIKE` + trigram indexes), not full-text ranking.
- The reason filter in the UI selects one reason at a time (the API accepts several).
- Next steps: auth + roles, an assignee field, CSV export, a restore endpoint for removed requests,
  and running the integration + E2E suites in CI on every push.
